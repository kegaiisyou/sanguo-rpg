## 0. 一句话结论（判断）

**不要按「兵力数字」自动在两套战斗之间切换，而要按「这场冲突的性质」选舞台。**

具体：让**玩家点的动作**明确宣告战斗性质（人对人的江湖冲突 → RPG 回合制；军队对军队/据点的军事行动 → 战棋），让**兵力**只负责「这个军事行动能不能发动、能带几个营」，让**叫阵**成为从战棋通往 RPG 的单向桥。全仓库只有一个判定函数、战前明说、两套结果各归各账。

理由很直接：兵力是**会跳动的量**（募兵、战损、断粮逃兵都能让它一夜之间从 300 变 0），用它当模式开关，玩家在同一地点打同一种敌人，昨天是卡牌、今天是棋盘，且无法预期 —— 这恰恰是「逻辑上讲不通」的来源。冲突性质则是**稳定的、玩家点之前就知道的**。

对草案的立场：**方向认同，判据不认同**。草案 §3/§8 的「统一分层 + 防困惑纪律 + 叫阵」值得保留，但草案把模式选择压在「两个数字」上，实际却并存三套互相冲突的判据（§2 评审意见 R1），且 §9 自己倾向推翻 §3.4 主规则。建议按本文 §3 收敛后再落地。

## 1. 事实基线：代码现在到底怎么分

### 1.1 两套战斗的「结算对象」根本不同（这是分流最硬的依据）

| | RPG 回合制（`shared/core/combat.js`） | 战棋沙盘（`shared/core/battlefield.js`） |
|---|---|---|
| 战后结算 | `02-玩法与系统.md:62`：修为 / 潜能 / 银两 / 声望；`:47-55` 指令五件套（普攻/招式/防御/道具/撤退） | `03-战棋沙盘系统.md:142-146`：`#bf-result` 回合数 / 存活营数 / 各营战绩表 |
| 结算落在 | **人**：`combat.js:815-843` 写 `pot`/`addXp`/`quest.*`/`lineExp`/`learnedMartial` | **军队与地盘**：`war.js:355` 兵损、`:420` 城池易帜、`:452-482` 军团溃散/聚落易帜 |
| 数值主轴 | 个人 `hp`、内功、武学、装备六槽 | 营级 `hp/atk/def/morale`、兵种克制、地形、阵型 |
| 共用 | 同一个 `showCombatSettlement`（`combat.js:938-975`） | 同左（另加独立 `#bf-result`） |

【判断】两套系统不是「同一场战斗的大小号版本」，而是**两套账**：一套结算个人成长，一套结算势力消长。因此分流不该问「多少人打」，该问「赢了之后记到哪本账上」。这也解释了为什么 `01-进度与待办.md:175` 会把「不动个人战、不出图」写成边界铁律。

### 1.2 现状三处判据，彼此不一致（事实）

| 位置 | 判据 | 结果 | 问题 |
|---|---|---|---|
| `engine.js:2665`（`case 'siege'`） | `armyActive()` 二元布尔 | true → `openSiegePrep` 战棋；false → `startCombat('city_guard')` RPG | **同一个按钮隐式两种战斗**，玩家完全无法预期 |

| `engine.js:4870 / :4892`（`engageFieldArmy` / `attackPlace`） | 无判据，硬编码 | 恒走 `startFieldBattle` 战棋 | 只校验 160km 与部曲在场，与草案 §3.3 决策表不一致 |

补充事实：
- `armyActive()` 定义在 `army.js:86`，只判 `a.active && armyCount()>0`，**没有任何规模阈值**。
- `shared/index.js:72` 开局即 `army:{active:true, troops:[{count:1}]}` → `armyActive()` 返回 true → 开局点「起兵略地」直接进三段攻城战棋。这正是草案 §1 所说「1 兵打城 = 政变感」的真实成因。
- `shared/**` 中**不存在**任何战斗模式枚举/常量/判定函数；检索 `ENCOUNTER_KIND`、`classifyEncounter`、`pickStage`、`RPG_TOTAL_CAP`、`battleMode` 等，全部只命中 `04-战斗分层与叫阵机制.md` 的伪码，代码 0 命中。
- 已有但未通用化的现成锚点：`engine.js:4702-4753` 完整单挑状态机 `renderDuel/duelPick/duelStart/duelRound/duelGo/duelSkip`，以及 `war.js:331-339` 的 `openModal('duel')`，目前**只在攻城且有名将守将时**触发。
- DQ 侧现有约 15 个入口（`engine.js:1724,1728,2011,2702,2843-2862`、`field.js:171,172,243,358,434`、`triggers.js:145`、`npc.js:203`、`companion.js:332`、`dev.js:110`），涵盖教学木人桩、剧情 BOSS、副本、郊野清剿、野怪。**它们是叙事/个人战斗，不是军队战斗的退化形态。**

- 已落地：`v20261112a` 开局即可带 1 兵对附近**聚落**攻掠（`attackPlace` → 野战战棋），E2E 已验证；`01-进度与待办.md:166-175`「零·军」四步闭环已完成。

## 2. 为什么「按规模自动切换」讲不通（判断，逐条带证据）

**R1 · 草案判据自相矛盾，实现出来必然玩家困惑。**
草案 §2 声称「所有判定只依赖两个数字（T 部曲数、hasCommander）」，但正文用了三套判据：§3.1 成军线 `T≥500`、§3.3 决策表（`T` × 敌方规模 × 有无首领）、§3.4 `pickStage()` 的「双方合计个体 ≤ 12」。更关键的是 §9 明确写「自动 RPG（人少跳过战棋）是否默认开启…倾向采用后者（永远先进战棋）」—— **这条倾向直接推翻 §3.4 的主规则**。评审前必须先消掉这个未闭合项，否则不同开发者会实现出两种游戏。

**R2 · 计数单位混用，「两个数字」推不出 `pickStage()`。**
`T = Σ troops.count`（`army.js:55-59`）是**人数**；`RPG_CAP_PER_SIDE = 6` / `RPG_TOTAL_CAP = 12` 是**上场独立单位数**。`pickStage(playerChampions, enemyChampions)` 的入参是「将领数」，与 `T` 无关。草案 §6 伪码里 `classifyEncounter()` 用 `E = enemy.troops`（人数）比较 `STRATEGY_LINE = 500`，而 `pickStage()` 用单位数比较 12 —— 同一场遭遇会同时得到「战略层」和「直接 RPG」两个结论，逻辑链是断的。

**R3 · 兵力是易变量，会造成「同地点同敌人、战斗界面跳变」。**
`army.js:196`（遣散）、`:347`（断粮逃兵）、`:500`（战后兵损）都会把 `a.active` 置 false，`:152/:183` 募兵又置 true。以它为模式开关，玩家在苦役营外打同一伙山贼，只因刚打完一仗损了兵，就从战棋变成卡牌。【判断】这是体验割裂，而草案 §8「触发规则全局唯一」想解决的正是这件事 —— 判据选错，纪律再严也补不上。

**R4 · 「成军线 = 500」与现状数值经济未校准，直接落地有回归风险。**
`army.js:60 armyCap()` 按 `title` 取兵力上限，募兵还受城兵源/府库限制（`army.js:128-158`）。草案 §9 自己也把「阈值需结合 `Settlement.compose` 的 3 营 5:3:2 再校准」列为未决项。若一期就上 500 线，会同时废掉 `v20261112a` 刚落地的「开局可开战」与 `engine.js:2665` 的现有战役入口，且 `city_guard`（`enemies.js:213`，攻城专用敌人）与 `combat.js:761-780` 的夺城结算分支一起变成死代码。

**R5 · 「战棋是底层通用舞台，人少也先进战棋」与现有内容体量冲突。**
`03-战棋沙盘系统.md:7` 确实把战棋定位为「剧情/地图遭遇战」舞台，但代码的 15 个 DQ 入口承载了教学、剧情 BOSS、副本、野怪等全部叙事战斗。全量改成「先进战棋再叫阵」等于重写全部叙事战斗表现与 `showCombatSettlement` 的养成回写，产能上不现实，也会破坏 `01-进度与待办.md:175`「不动个人战」的边界约定。

## 3. 建议方案：三层判定模型

### 3.1 第一主轴：交战对象性质决定舞台（替代「规模决定舞台」）

定义唯一概念：`intent`（玩家意图 / 冲突性质），由**发起点显式声明**，不由兵力推算。

| `intent` | 语义 | 舞台 | 典型发起点（现状入口） |
|---|---|---|---|
| `personal` | 人对人的江湖冲突、剧情对决、清剿野兽匪徒、教学 | **RPG 回合制** `combat.js` | `engine.js:1724/2011/2702/2843-2862`、`field.js:*`、`triggers.js:145`、`npc.js:203` |
| `military` | 军队对军队 / 对据点的军事行动 | **战棋** `battlefield.js` | `war.js:306/512/547`、`engine.js:4852/4873`、`engine.js:2666` |
| `duel` | 战棋内主将过场 | **RPG 过场 → 回写战棋** | 二期，`war.js:331-339` 已有锚点 |

【判断】这条主轴与代码现状**几乎完全吻合** —— 现有 15 个 DQ 入口和所有战棋入口本来就是按对象性质分开的。所以本方案不是推翻重来，而是**把implicit 事实收敛成一个函数并显式化**，改动面最小、语义最自洽。真正需要修的只有 `engine.js:2665` 一处「同按钮两模式」。

### 3.2 第二层：兵力降级为「准入 + 编成」，不再是模式开关

- **准入**：军事行动需部曲在场（`armyWithPlayer()`、`armyCount()>0`），沿用现有校验即可；战役级（攻城）可在三期引入成军线，但必须先按 `armyCap(title)` 与募兵经济校准，且**只对 `military` 生效，不触及 `personal`**。
- **编成**：兵力决定战棋 `scale`（`war.js:275` 已有 `siege/field/skirmish`）与营数，与模式无关。
- **拦截**：不满足准入时 `toast` 明确提示「势单力薄，先募兵」，**绝不偷偷降级成另一套战斗**（草案 §3.3 的「不可战拦截」这一条完全正确，应保留）。

### 3.3 第三层：单一决策函数 + 显式覆写 + 战前宣告

```
resolveCombatMode(ctx) -> { mode, intent, reason, label }
  ctx = { forceMode?, intent?, targetKind?, enemy?, playerTroops?, source }
```

优先级（从上到下，命中即返回）：

1. `ctx.forceMode` —— 剧情脚本 / 教学 / 调试台显式指定，最高优先（保住 `camp_dummy` 教学战、剧情 BOSS 的确定性）。
2. `ctx.intent` —— 发起动作自己声明性质（主判据）。
3. `targetKind` 兜底 —— 野怪/剧情 BOSS/NPC → `personal`；城池/军团/聚落/关隘 → `military`。
4. 无法判定时默认 `personal` 并记日志（保守：不误开大战场）。

返回结果里的 `label` 直接供 UI 使用，做到**判定与告知同源**，避免文案与实现漂移。

配套三条纪律：
- **全局唯一**：`engine.js:2665`、`war.js:273`、`engine.js:4870/4892` 三处硬编码全部改调 `resolveCombatMode()`；新增入口一律走它，禁止再写 `if(armyActive())` 式的隐式分流。
- **战前宣告**：`war.js:582` 编成面板与 DQ 开场各加一行「本战性质：…」，沿用草案 §5 的遇敌弹窗文案（草案这一节质量高，建议直接采纳）。
- **各归各账**：`personal` 只写个人成长字段，`military` 只写势力字段；遵守 `settlement.js:3-4` / `fieldarmy.js:3` 的「不改 `cityOwner`/`ruledCities`/`cityWards`」隔离铁律，两套结算共用 `showCombatSettlement` 但不互相写字段。

### 3.4 把「同按钮两模式」拆成两个显式动作（一期最关键的修复）

【判断】这是全案最值钱的一处改动：系统不该猜玩家想打个人战还是战役，**让按钮自己说清楚**。

| 动作 | intent | 舞台 | 前置 |
|---|---|---|---|
| 「起兵略地」 | `military` | 恒战棋（三段攻城） | 部曲在场 + （三期）成军线 |
| 「潜入 / 单骑闯营」 | `personal` | 恒 RPG，复用现成 `city_guard` + `combat.js:761-780` 夺城结算 | 剧情/身份条件 |

收益：`v20261112a` 刚修好的 DQ 撤退路径（`endCombat` 的 `fled` 空 class 修复）不会被浪费；`city_guard` 与 `siegeWin/siegeLose` 从「隐式退化分支」升格为「有名字的正经玩法」；玩家点之前就知道会看到棋盘还是卡牌。

注意：这改变了按钮与交互模型，按 `DESIGN_SYSTEM.md:48`「任何改动交互模型都需**显式**用户确认」，故本文只提方案、不动代码（见 §10 待拍板 P1）。

### 3.5 修订后的决策表（替换草案 §3.3 + §3.4，消除 R1/R2）

| 玩家动作 / 对象 | 准入 | 舞台 | 兵力作用 |
|---|---|---|---|
| 郊野野兽、剧情 BOSS、教学、副本 | 无 | RPG | 无（个人数值） |
| 敌意 NPC 挑战、山贼头目 | 无 | RPG；头目可在二期提供「叫阵」入口 | 无 |
| 聚落攻掠 / 劫掠（`attackPlace`） | 部曲在场 + 160km | 战棋（`skirmish` 规模） | 决定营数/scale |
| 大地图部队接战（`engageFieldArmy`） | 部曲在场 + 160km | 战棋（`field`） | 决定营数/scale |
| 起兵略地 / 攻城（`siege`） | 部曲在场 +（三期）成军线 | 战棋（`siege`） | 决定营数/scale；不满足则 `toast` 拦截，不降级 |
| 逐鹿防守（`defend`） | —— | **二期再统一**为战棋；一期保留现状 | —— |
| 战棋中「叫阵」 | 敌方有名将 | RPG 过场 → 回写 `rout`/士气 | 不影响舞台 |

### 3.6 统一模型（一句话 + 核心循环文字环）

> 战棋管「地盘与军队」，RPG 管「人与恩怨」，叫阵是从前者通往后者的一座单向桥；系统只根据「你点了哪种行动」选舞台，兵力只决定「能不能上、带多少人上」。

核心循环文字环（策划案纪律：一句话说清玩家每 1–3 分钟在做什么）：

```
行旅/探索 → 明确选择「个人应战」或「举兵行事」 → 战前宣告本战性质
→ 进入对应舞台 → 结算各归各账（修为 / 地盘） → 回到行旅
```
