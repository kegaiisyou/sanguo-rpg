# 02 · 开发流程与版本迭代

> 每次改代码都按本文走。跳过步骤的代价通常是"改了但线上没变"，且极难察觉。

---

## 一、为什么必须先懂 bundle

浏览器**不直接加载 `shared/` 下的散装模块**，而是加载单个 `shared/bundle.js`（约 1.3MB 未压缩 / 0.79MB 压缩）。

- `shared/*.js` 是给人读和编辑的**源码**；
- `shared/bundle.js` 是给浏览器跑的**产物**；
- 二者靠 `tools/bundle.py` 同步。

**只读源码 / 只改源码而不跑 bundle = 改动完全不生效。**
更糟的是它不报错、版本号照常显示（`index.html` 里写着，与 bundle 内容无关），所以历史上出现过"仓库里提交的 bundle 落后源码好几个迭代"的情况 —— 详见 [05-恶性Bug与陷阱清单 #1](05-恶性Bug与陷阱清单.md)。

---

## 二、标准改动流程

```
① 改源码 shared/xxx.js
       ↓
② python tools/bundle.py      ← 必须跑两次（见下）
       ↓
③ 版本号三处对齐（若跨版本迭代）
       ↓
④ node --check shared/bundle.js
       ↓
⑤ node test/syntax_check_all.js && node test/cross_reference_check.js
       ↓
⑥ 浏览器实测主流程（0 pageerror）
       ↓
⑦ git commit + push（见 03-GitHub与发布）
```

### 为什么要跑两次 `bundle.py`

`bundle.py` 的执行顺序是：**先按磁盘上的源码拼接 → 再 bump 版本号**。

所以：
- 第一次跑：用磁盘上的旧 constants 拼进 bundle，然后把磁盘 constants 改成新版本号；
- 第二次跑：才读到刚 bump 过的新版本号。

只跑一次 → bundle 内部版本号与磁盘不一致。

### 修改后必须核验

```python
# 三处是否一致
print open('shared/config/constants.js')   # VERSION: '20261029e'
print open('tools/bundle.py')              # VERSION = '20261029e'
print open('index.html')                   # bundle.js?v=20261029e / game.css?v=20261029e
```

## 三、版本号规则

### 来源与格式

- **唯一来源**：`shared/config/constants.js` 里的 `LF.CONSTANTS.VERSION`
- 格式：`YYYYMMDD + 字母序号`，如 `20261029e`（同一天多次迭代按 a/b/c…递增）
- 屏上显示位置：标题页 `.tt-ver`、状态栏 `.st-ver`

### ⚠️ 不要动 `defaultSave.version`

`shared/index.js` 的 `defaultSave.version = '0.2.0'` 是**存档 schema 版本**，用于存档兼容/迁移，**与显示版本无关**。改动它可能导致旧存档读不了。

### ⚠️ `tools/bundle.py` 里的 VERSION 是硬编码

它是构建末尾用来覆盖 constants 的那一行。**想改版本必须先改 `bundle.py` 的这一行**，只改 `constants.js` 会被打回原值。

## 四、三处同步清单（checklist）

| # | 位置 | 由谁维护 |
|---|---|---|
| 1 | `shared/config/constants.js` → `VERSION: '...'` | 手动 or 由 bundle.py 覆盖 |
| 2 | `tools/bundle.py` → `VERSION = '...'`（**硬编码，必须手动**） | 手动 |
| 3 | `index.html` → `<script src="shared/bundle.js?v=...">` | **bundle.py 自动** |
| 4 | `index.html` → `<link href="shared/css/game.css?v=...">` | **手动**（bundle.py 不碰 link 标签） |

**第 4 条最容易忘**：改了 `game.css` 但没 bump `game.css?v` → 浏览器拿旧缓存，样式不生效。

---

## 五、新增模块必须登记 manifest

`tools/bundle.py` 按 **`tools/bundle.manifest` 显式清单**拼接（不是 glob 目录）。

**新建模块忘了登记 → `LF.createXxx` undefined → engine 直接崩。**

登记时注意**顺序**：必须在依赖它的模块之前。例如 `engine.js` 调用 `NpcAi`，则 `shared/core/npcai.js` 要排在 `shared/core/engine.js` 之前。

---

## 六、css 特殊说明

`shared/css/game.css` **不在 bundle 内**，是独立 HTTP 请求 + 独立缓存参数。
改动流程：改 css → 手动改 `index.html` 的 `game.css?v=` → 不需要重跑 bundle.py。

## 七、宝宝级命令备忘

```bash
# 重建 bundle（连跑两次）
python tools/bundle.py && python tools/bundle.py

# 语法校验
node --check shared/bundle.js

# 一键校验「版本四源一致 + bundle 是否已重建」（专门抓历史坑 A/B）
python tools/verify_versions.py

# 三道门禁
node test/syntax_check_all.js          # 语法错误数
node test/cross_reference_check.js     # 悬空引用 / VERSION 显示
node test/prelink_gate.js              # 启动期错误（见下方注意）
```

### ⚠️ `prelink_gate.js` 的现状说明

该门禁用 jsdom 加载 bundle。由于 **jsdom 未实现 `HTMLCanvasElement.getContext`**（未安装 canvas npm 包），它会报：

```
jsdomError: Not implemented: HTMLCanvasElement.prototype.getContext
```

这**不是代码回归**，是环境限制。判断标准是看**引擎有没有正常起来**：

- ✅ 看到 `bootedGame=true | getState()=ok` 且工厂列表齐全 → 正常，这类 jsdomError 可忽略
- ❌ 若 `window.openModal` 未暴露 / `LF.createPanels` 缺失 → 真崩了（见 05 文档 #9）

不要因为这条恒黄/恒红就无视整个门禁 —— 建议后续给 CI 装 canvas 包或显式豁免环境类错误。
