# 城市营造系统 · 核心数据模型设计文档（阶段一：地基）

> 目标：把"玩家微观建造"与"委派 NPC 宏观建造"统一到**一个数据模型**上，先落地第 1–3 步（材料前置 / 城市等级动态 / BuildOrder + cityCells 覆盖层），并勾连第 4–6 步（图纸 / 政令台 / NPC 培养·流亡）。

---

## 0. 范围与原则

- **一个工单模型统一微观与宏观**：玩家自己建 = `requester:'player'`（现场投料、按 `exert` 推进）；委派 NPC 建 = `requester: <npcId>`（后台按天推进、占用 NPC）。其余字段完全一致。
- **数据驱动**：加一种建筑 = 加一条 `BLUEPRINT` 数据，不写分支逻辑。`NPC_GEN` 已是数据驱动，格子类型变 → NPC 自动变（免费）。
- **复用现有钩子，不造轮子**：
  - `advanceTime(n)` 已有 `tickForge(n)`（index.html:5325）→ 挂 `tickBuildOrders(n)`。
  - `state.day` 跨子夜累加（index.html:3107）→ 工期 / 租金按天结算。
  - `state.placed`（index.html 冶炼坊放置物）→ 城市建筑实例持久化参考同款。
  - `GRID_VER`（index.html:3927）→ 城市等级 / 布局改动后自增，旧档自动重建。

---

## 1. 总体架构：分层营造

```
┌─ 宏观层（委派）─── 政令台 → BuildOrder(requester=npc) → tickBuildOrders 按天推进 → 完成
│                                                                           ↑ 占用 NPC 状态
└─ 微观层（现场）─── 地点「营造」按钮 → 选图纸 → BuildOrder(requester=player)
                                                                   ↑ 现场投料 / exert 推进
                        两者最终都落进同一个 cityCells 覆盖层（格子类型 + level）
```

政令台**不是新逻辑**，只是 BuildOrder 的"委派入口 + 命令分类标签（治理/人事/军事/外交）"。

## 2. 核心数据模型

### 2.1 城市等级（动态，替代固化 `c.grid`）

存储：`state.flags.cityLevel = { [cid]: level }`（缺省时由 `c.tier` 映射初始级）。

> 修订（v2）：原 `[2,3,4,7,9]` 跨度不均（4→7→9 断层），且命名缺基层层级。改为**每次 +1 的平滑网格序列 `[2,3,4,5,6,7,8,9]`**，命名贴合东汉行政区划与基层聚落（州—郡—县之下有乡/亭/里/聚、豪强坞堡；汉末州牧驻节常称"府"）。

等级表（命名依据史料，grid 平滑递增）：

| level | 名称 | 史实依据 | grid size | 说明 |
|---|---|---|---|---|
| 0 | 村/村落 | 坞壁、聚（豪强自保，王莽天凤年间已普及；称"村"更合玩家认知） | 2×2 | 玩家城最起步（如小沛初领） |
| 1 | 镇 | 亭（亭为县下治安/市集单位，民间多称"镇"） | 3×3 | |
| 2 | 乡 | 乡（县下行政单位） | 4×4 | |
| 3 | 县城 | 县 | 5×5 | 现有 xian（原 grid5，不动） |
| 4 | 郡城 | 郡 | 6×6 | 现有 zhou 原为 7，下调到 6 以平滑 |
| 5 | 府城 | 府（汉末州牧/都督驻节称"府"，如都督府） | 7×7 | 新增，填补 6→9 缺口 |
| 6 | 州城 | 州（州治） | 8×8 | 现有 zhou 升格路径 |
| 7 | 都城/京畿 | 京师（曹操修许昌为许都即此） | 9×9 | 现有 capital |

```js
// 派生：城市当前网格边长（替换原 c.grid 取值，平滑序列 2→9 每次 +1）
var CITY_LV_SIZE = [2,3,4,5,6,7,8,9];
function cityGridSize(cid){
  var lv = (state.flags.cityLevel && state.flags.cityLevel[cid]);
  if(lv==null){
    var c=(LF.CITIES||{})[cid]||{};
    lv = (c.tier==='capital')?7 : (c.tier==='zhou')?4 : (c.tier==='xian')?3 : 0;
  }
  return CITY_LV_SIZE[lv] || 3;
}
```

- **升级**：消耗材料 + 工期（走 BuildOrder，蓝图 `bp_city_up`）；升级后改 `cityLevel[cid]` 并自增 `GRID_VER`（旧网格自动重建，新边缘格先为 `unbuilt`）。每次仅 +1 级、网格 +1 圈，手感连续。
- **降级**：战争 / 政变 / 匪患 → `cityLevel-1`，触发**流亡**（见 §3）。
- **兼容性**：现有城市初始 lv 由 `c.tier` 映射（xian→3、zhou→4、capital→7）；`genCityGrid` 不再读 `c.grid`，统一走 `cityGridSize`；旧档自增 `GRID_VER` 自动重建，无丢失。

### 2.2 cityCells 覆盖层（玩家 / NPC 建造实例）

存储：`state.flags.cityCells = { [cid]: { "x,y": CellInst } }`

```js
CellInst = {
  type:'market'|'home'|'barracks'|'farm'|'road'|'gov'|'palace', // 覆盖 base 的类型
  level: 1,                 // 建筑等级（商铺数 = f(level)）
  shops: ['yaofu','buzhuang', ...],  // 仅 market：玩家招商入驻清单（非程序生成）
  owner:'player'|npcId|faction,      // 产权（租金归属）
  built: true|false,        // false = 施工中（覆盖层存在但显示工地）
  buildOrderId: '...',      // 关联工单（施工态时引用）
}
```

### 2.3 BuildOrder（统一工单，微观/宏观共用）

存储：`state.flags.buildOrders = { [orderId]: BuildOrder }`，另 `state.flags.buildOrderSeq` 自增。

```js
BuildOrder = {
  id, cid, x, y,
  blueprintId,            // 指向 BLUEPRINT（建造/升级/营造）
  requester:'player' | npcId,   // ★ 微观 vs 宏观的唯一区别
  level,                  // 目标建筑等级
  matsNeeded:{ stone:500, brick:1000, wood:300, food:100 },  // 全量总需求
  matsPaid:{ stone:0, ... },     // 已投入（微观现场逐步投；宏观委派时一次性扣或分期）
  laborNeeded: 800,       // 总人力（民夫/民壮工时）
  laborPaid: 0,
  moneyPaid: 0,           // 酬劳 / 图纸费
  stages:[ {name, needMat:{...}, needLabor:n}, ... ],  // 复用 LF.BUILD.stages 结构
  stageIndex: 0,
  startDay: state.day,
  estDays: 12,            // 宏观：由 requester 建造属性决定；微观不设（按 exert 推进）
  status:'queued'|'building'|'done'|'paused',
  assignedNpc: null | npcId,   // 宏观占用该 NPC
}
```

**微观推进**：玩家在地点点「营造」→ 弹图纸 → 现场 `packConsume` 材料 / 扣 `exert('营造')` 推 `laborPaid`，满则 `built=true` 写入 cityCells。
**宏观推进**：`tickBuildOrders(n)` 按 `estDays` 每日推进；`assignedNpc` 标记占用（不可再派其他令）；完成写 cityCells、释放 NPC。

## 2.4 资源产出建筑（商业/军事/居民三区之外）

史料锚点：汉代**盐铁官营**（武帝元狩四年置盐官37处、铁官48处，产盐铁区设专官）；**屯田制**（曹操许下屯田，分民屯/军屯，设典农官）；另有木官掌山林。据此，城市内部除商业/军事/居民三区，还应包含资源产区：

| 类别 | 建筑 type | 史实依据 | 产出 | 备注 |
|---|---|---|---|---|
| 农业 | `farm` | 民屯/军屯、典农官 | 粮（稳定产，扩现有助农） | 已有基础，升级为每日产出 |
| 林业 | `wood` 伐木场/林苑 | 木官（掌山林） | 木材 wood | 补材料产线第 1 步 |
| 矿区·石 | `quarry` 采石场 | 采石崖已存在 | 石料 stone | 已有，纳入统一管理 |
| 矿区·铁 | `iron` 铁官/冶铁 | 铁官（48处） | 铁锭 tieding | 复用 `bp_yeolian` 冶炼 |
| 盐业 | `salt` 盐官/盐场 | 盐官（37处，海盐县等） | 盐（硬通货/交易物） | 沿海/产盐城专属 |
| 工坊 | `forge`/`kiln` 工官坊/砖窑 | 工官（掌手工业） | 砖 brick、器械 | 砖窑为材料产线关键 |

**统一规则**：所有资源建筑都是一条 `BLUEPRINT`，对应一个 `type`。`NPC_GEN` 自动为其配"庄头/铁官/盐户/林官"等 GenNPC（零额外 NPC 代码）。产出走与 `tickBuildOrders` 同款的 `tickResource(n)`（挂在 `advanceTime`），按天结算、入 owner 钱袋/背包。盐、铁等可同时作为交易物与建造材料，形成"产区→市场→建造"闭环。

## 3. 城市等级动态 + 流亡

- **升级**：`bp_city_up` 工单完成 → `cityLevel[cid]++` → `GRID_VER` 自增 → `genCityGrid` 重建（更大网格，新边缘 `unbuilt`）。玩家在旧网格建的 `cityCells` override **保留**（不依赖程序生成 markets），因此不会丢失。
- **降级（流亡触发）**：`cityLevel[cid]--` → 网格缩小 → 超出新半径的 `cityCells` override 被删除（建筑"消失"）；其商铺 / 民户逻辑上"流亡到附近城镇"——实现上：被删 override 记为 `state.flags.refugees[cid].push({type,level})`，在附近已建成城镇 `renderCityStat` 提示"流民来投"；程序生成群众 NPC 无需迁移（无个体）。

## 4. 覆盖层与叠加顺序（解决"覆盖层打架"隐患）

修改 `cellDisplayType`（index.html:3834）为固定四层，从高到低：

```
override(cityCells 已建) > broken(掘断) > ruin(焦土) > base(程序生成 + devRadius/unbuilt)
```

- **施工中**（`override.built=false`）：显示"工地（🚧）"，`canEnterCell` 返回 false 或进入显示"施工中，堆满建材与工匠"。
- 优先级清晰：玩家建造 > 人为断路 > 战火焦土 > 原始布局。任一时刻只取最高层，杜绝互相覆盖的 bug。

## 5. tickBuildOrders 结算钩子（后台建造 + 租金）

在 `advanceTime` 末尾（紧跟 `tickForge(n)`，index.html:3115）加：

```js
function tickBuildOrders(n){
  var bo = state.flags.buildOrders; if(!bo) return;
  for(var id in bo){
    var o=bo[id]; if(o.status!=='building') continue;
    if(o.requester==='player') continue;       // 玩家单靠 exert 推进，tick 不代推
    // 宏观：按 estDays 每日推进（受 assignedNpc 建造属性加速）
    var mul = npcBuildSpeed(o.assignedNpc);     // 诸葛亮≈快，庸官≈慢
    o.laborPaid += Math.ceil(o.laborNeeded * (n / o.estDays) * mul);
    o.matsPaid  = o.matsNeeded;                 // 委派时一般已一次性备料
    if(o.laborPaid >= o.laborNeeded){ o.status='done'; commitBuild(o); releaseNpc(o.assignedNpc); }
  }
  // 每日租金：遍历已建 market override，按 level 收租入 owner 钱袋
  collectRents();
}
```

`collectRents()`：对每个 `cityCells` 中 `type==='market' && built` 的实例，按 `level` 满铺位收简单商业税（默认定额租金，参考汉代"市租"），入 `owner` 钱袋。

## 5.5 NPC 生成系统：统一模板 + 惰性生成属性（系统地基）

### 核心决策
- **不保留"两套 NPC 体系"**：GenNPC（无个体）与 IndivNPC（有属性）改为**同一张 `NPC_DB` 表 + 一个 `makeNpc` 工厂**。区别只有一个布尔：`official`（是否已登用/入队）。这样社交层（羁绊）与政务层（委派）天然打通，零分支。
- **属性惰性生成**：普通 NPC（店小二等）初始 `attr:null`，不占存档；当玩家与其建立羁绊并**登用/入队**时，调用 `grantAttr(id)` 一次性按模板补属性。避免"上千百姓全带属性"的浪费，也避免"有/无属性两套代码路径"。

### 数据模型
```js
// 统一工厂：所有 NPC 不论来源都经此生成
function makeNpc(base){
  // base: { id, name, type:'xiaoyer'|'baixing'|'guan'..., faction? }
  return {
    id: base.id, name: base.name, type: base.type,
    faction: base.faction || null,
    favor: 0,            // 好感度（送礼/任务累积）
    bond: 0,             // 羁绊值
    bondQuest: null,     // 入队/登用前置任务链 id
    official: false,     // ★ false=社交对象(Gen)/true=可委派(Indiv)
    enlisted: false,     // 是否已在玩家队伍/僚属
    attr: null,          // 惰性：登用时再 grantAttr
    busyUntil: 0, level: 0, exp: 0, loyalty: 50
  };
}
// 登用/入队时一次性补属性（按 type 给默认五维）
function grantAttr(id){
  var n = NPC_DB[id]; if(!n || n.attr) return;
  var tpl = NPC_ATTR_TPL[n.type] || NPC_ATTR_TPL._default;
  n.attr = { 政:tpl.政, 建:tpl.建, 统:tpl.统, 智:tpl.智, 武:tpl.武 };
  n.official = true;
  state.flags.officers[id] = n;   // 进入委派池
}
```

### 羁绊 → 登用 → 委派 闭环
1. 玩家与 NPC 交谈/送礼/完成委托 → `favor↑`、推进 `bondQuest`。
2. `favor≥阈值` 或 `bondQuest` 完成 → 出现「邀请入队 / 登用」选项。
3. 确认 → `grantAttr(id)` → `official=true`、`enlisted=true` → 进 `officers` 池。
4. 政令台从 `officers` 派令（建造/征兵/训练），`busyUntil` 占用；完成令 `exp↑`→`level↑`→属性成长。

### 与现有 `NPC_GEN` 的衔接
- `NPC_GEN`（index.html:3656）继续按格子类型自动生成交互用 NPC，但它生成的记录**写入 `NPC_DB`**（带 `official:false`、`attr:null`），不再是"无个体不可追"——玩家可对集市店小二送礼建立羁绊，后续登用。
- `NPC_GEN` 本身代码可基本不改，只需把"生成的 NPC 注册进 `NPC_DB`"；未交互的纯氛围 NPC 不注册（保持零维护）。
- 城主府/政令台只从 `officers`（即 `official:true`）派令。

### NPC 属性模板 `NPC_ATTR_TPL`（示例）
| type | 政 | 建 | 统 | 智 | 武 | 说明 |
|---|---|---|---|---|---|---|
| xiaoyer 店小二 | 25 | 20 | 15 | 30 | 10 | 低，但可培养 |
| baixing 百姓 | 20 | 25 | 15 | 20 | 15 | |
| guan_liang 良臣(诸葛亮型) | 90 | 85 | 70 | 95 | 40 | 建造极快 |
| guan_yong 庸官 | 40 | 35 | 30 | 40 | 30 | 慢 |
| _default | 30 | 30 | 30 | 30 | 30 | |

> `attr.建` 直接驱动 `npcBuildSpeed(npcId)`（文档 §5 的 `mul`）：良臣≈1.8、庸官≈0.6。

## 6. 材料经济前置（第 1 步，必须最先做）

建造消耗巨大（砖/石/木以百千计），现有**仅采石崖产石料**。需补伐木与砖窑两条产线。材料进 `state.pack`，建造工单 `BuildOrder.matsNeeded` 用 `packConsume` 扣。**材料产线不做，建造系统即空转——阶段一最先落地。**

### 6.1 实现思路（复用 `LF.BUILD` 多阶段范式）
现有 `LF.BUILD.bp_yeolian`（冶炼坊）已是"挖矿→运料→砌炉→试火"的多阶段蓝图范式（`need`/`done`/`interior` + `stages`）。伐木场/砖窑**完全照搬**：

| 产线 | 蓝图 id | 备料阶段 need | 落成后产出动作 | 产出 |
|---|---|---|---|---|
| 采石 | 已有（采石崖，index.html:5201） | — | 「采石」 | 石料 stone |
| 伐木 | `bp_woodcamp` | `{wood:0}`（无前置料，或需简单工具） | 「伐木」 | 木材 wood |
| 砖窑 | `bp_yaolu` | `{stone:N, wood:M}`（石料+燃料） | 「烧砖」 | 砖 brick |

- **放置方式**：两者皆可——野外靠近林地/黏土坡的地点用 `state.placed`（仿冶炼坊）；城市内 `forge`/`empty` 格用 `cityCells` 覆盖层。共用 `BLUEPRINT`，仅落地存储不同。
- **产出动作**：落成后在对应地点/格子 `cityCellActs` 加「伐木」「烧砖」按钮，调 `packGain(wood/brick)`，扣 `exert`（即时）或挂 tick（派 NPC 守自动产，复用 `tickForge` 同款模式）。

### 6.2 落地步骤（编码顺序）
1. **build.js**：仿 `bp_yeolian` 加 `bp_woodcamp`、`bp_yaolu` 两条蓝图（含 `stages`/`need`/`done`/`interior`）。
2. **资源地点标记**：野外可营造地点加 `wood`/`clay` 标记，或允许在城市 `forge`/`empty` 格造。
3. **index.html 动作**：在对应地点/格子动作里加「伐木」「烧砖」，调 `packGain`；收纳进 `cityCellActs` / 地点 `acts`。
4. **校验**：`node --check build.js` + 抽取 index.html 内联脚本 vm 编译（沿用 `_syntax_check.js`），确认 0 语法错误。
5. **联动验证**：造砖窑→烧砖→`pack` 出现 brick→后续 `BuildOrder` 可 `packConsume` 扣砖（第 3 步打通）。

## 8. 实施里程碑（建议顺序）
